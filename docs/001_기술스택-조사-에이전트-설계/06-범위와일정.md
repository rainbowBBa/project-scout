# 06 · 범위와 일정

← [문서 목록](README.md)

2일이라는 예산이 이 문서의 모든 결정을 지배한다. 이 파일은 **무엇을 안 만들기로 했는지**와
**시간이 부족할 때 무엇부터 버릴지**를 미리 못 박아둔 곳이다.

## 프로토타입 규모 — 작게 시작해서 플래그로 키운다

| 파라미터 | 프로토타입 기본 | 풀 규모 | CLI 플래그 |
|---|---|---|---|
| `analyze` 도출 요소 | 6~10개 (전부 저장) | 동일 | — |
| `search` 통과 요소 | **3개** | 8개 | `--max-components` |
| 요소당 후보 | **3개** | 5개 | `--max-candidates` |
| 총 후보 | **8~10개** | 30~40개 | |
| judge 호출 | **8~10회** | 30~40회 | |
| dossier 수집 시간 | ~1분 | ~3분 | |
| 1회 실행 토큰 | 입력 100~150k | 300~400k | |

기본값을 작게 둔 이유는 **한 번 돌리고 눈으로 확인하는 주기가 짧아야** 하기 때문이다.
Day 2 오후에 `verify` 프롬프트를 20번 고칠 텐데, 매번 3분 + judge 40회를 기다릴 수 없다.

부수 효과: 후보 10개면 MCP 호출이 30건 정도라 **GitHub 토큰 없이 1회 실행이 된다**
(미인증 60req/h).

**트레이드오프**: 요소당 2~3개면 사실상 "1위 + 대안 1~2개"라 비교의 값이 얕다.
파이프라인 작동 검증에는 충분하지만, 실제 의사결정에 쓰려면 플래그를 올려야 한다.
그래서 규모를 상수가 아니라 **플래그**로 뺐다.

## 의도적으로 잘라낸 것

| 뺀 것 | 이유 / 나중에 |
|---|---|
| 별도 `design` 단계 (아키텍처 후보 2~3안) | `analyze`의 `approach_notes`로 흡수. 자리는 `analyze` 다음 |
| ADR 생성 | 보고서 한 섹션으로 축약 |
| `domains/` 모듈 (웹·AI 도메인별 기준) | 도메인 힌트를 `analyze` 프롬프트 문자열로 |
| MCP 툴 3종 (`web_fetch`, `npm_downloads`, `depsdev`) | 6종만 남김 |
| **평가 가중치** (`interview` 도출 + 가중 합산) | 배수 근거가 임의적이고 튜닝할 시간이 없다. judge가 `refined_brief`를 직접 읽는다 |
| **기준별 LLM 점수 3종** (`fit`·`team_fit`·`exit_cost`) | 재료가 `verify`의 `solves_reason`/`pros`/`cons`/`caveats`에 있고, 따로 매기면 judge가 평균해 `overall`을 낼 유혹이 커진다. `overall` + `score_reason` 하나로 대체 |
| 평가 기준 2종 (`ecosystem`, `ops_cost`) | 다운로드 추이·정성조사가 필요 |
| judge 다수결 (self-consistency) | 후보당 3회 판정은 2일에 과함. 구조만 잡고 상수만 바꾸면 되게 |
| listwise 비교 judge | pointwise + `evaluate` 비교로 대체 |
| streamable-http 전송 | stdio만. FastMCP에서 전환은 한 줄 |
| 체크포인트 무효화 로직 | 재개만 (거의 공짜) |
| 프롬프트 캐싱 | Bedrock 자동 캐싱 미지원. 비용만 증가, 기능 손실 없음 |
| CI 파이프라인 | 로컬 `uv run` 4개로 충분 |

가중치를 뺀 결과 **예산이 갈 곳을 잃는 문제도 함께 사라졌다.** 예산·팀·데드라인은
`refined_brief` 한 문단으로 judge에게 그대로 전달되고, judge가 읽고 판단한다.
5기준에 억지로 대응시킬 필요가 없어졌다 —
[stages/4-evaluate.md](stages/4-evaluate.md)에서 설명한다.

## 일정 — 설계 시점의 추정

> **실행 순서는 [002 개발계획](../002_개발계획/README.md)이 정본이다.**
> 002는 `interview`부터 순차로 만들도록 순서를 바꿨다(의존성 근거: `interview`·`analyze`는
> MCP가 필요 없다). 아래 표는 설계 시점의 시간 추정으로 남긴다.

### Day 1 — MCP 서버 (인터넷 출구부터)

| 시간 | 작업 | 완료 기준 |
|---|---|---|
| ~1.5h | uv 설치 → 워크스페이스 스캐폴드 → ruff/ty → `scout doctor` | `uv sync` + `uv sync --package scout-net-mcp` 성공, Sonnet 1회 호출 성공, [07-검증](07-검증.md) M0 항목 해소 |
| ~2h | `egress.py` allowlist + 레이트리밋 + `cache.py` | `test_egress.py` 통과 |
| ~2.5h | providers `npm` · `pypi` · `osv` | 서버 단독 실행, 툴 직접 호출로 응답 확인 |
| ~2h | providers `github` · `search`(DDG) | 후보 10개 dossier 수집이 1분 내 |

**Day 1 종료 시점에 MCP 서버가 앱 없이 완결**되어야 한다.

왜 서버를 먼저 만드는가: 인터넷 출구가 사내 최대 제약이고, 여기가 막히면 나머지가 무의미하다.
그리고 서버는 앱 없이 단독 테스트가 되므로 **리스크를 가장 빨리 없앤다.**

## 뒤처질 때의 절단선

당일에 판단하면 보통 잘못된 걸 버린다. 순서를 미리 못 박는다.

### 1. `osv_query`

취약점 조회를 뺀다. `risk` 근거가 일부 손실되지만(라이선스·archived는 남는다)
나머지는 그대로 동작한다.

### 2. `method` kind 후보

아키텍처·개발방법은 `analyze`의 `approach_notes`로만 다루고 후보 판정은 생략.
`library`·`software`만 후보로 올린다. 후보 수가 8~10 → 6~8로 줄어 `verify` 시간도 준다.

### 3. grounding check의 재판정 루프

위반을 검출하고 표시만 하고, 프롬프트에 넣어 다시 물어보는 단계는 생략한다.

### 4. `report.html`의 꾸밈

막대 차트와 `<details>`는 CSS 한 줄 · HTML 태그 하나라 사실상 공짜이므로 남긴다.
다크모드와 배지 색상이 먼저 잘린다.

### 5. `interview` 되묻기

대화형 질문을 없애고 고정 기본 제약조건으로 대체한다. 가정은 보고서에 명시된다.

## 버리지 않는 것

### `web_search`

`method` 후보(아키텍처 패턴, 개발 접근법)의 **유일한** 근거다. 레지스트리에 조회할 API가
없기 때문이다. 절단선 2번으로 `method` 후보 자체를 버리는 게 순서상 먼저다.

### grounding 검출

절단선 3번으로 재판정 루프를 버려도 **검출은 남긴다.** 검출이 사라지면 judge를 신뢰할 근거가
없어지고, 그러면 이 도구는 그냥 LLM에게 물어보는 것과 같아진다.

### `analyze`의 `necessity`

가장 값어치 있는 기능이라 절단 대상이 아니다. 오히려 이걸 잘 하면 후보 수가 줄어
뒷 단계가 빨라진다.
