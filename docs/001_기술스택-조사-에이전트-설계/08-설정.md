# 08 · 설정과 환경변수

← [문서 목록](README.md)

설정은 `.env` 하나에 모으고 `pydantic-settings`로 읽는다.
이 파일이 **설정 항목의 단일 목록**이다 — 다른 문서에 흩어져 있던 값을 여기 모았다.

## 앱(`scout`) 전용

MCP 서버 프로세스에는 넘기지 않는다.

| 변수 | 기본 | 설명 |
|---|---|---|
| `AWS_DEFAULT_REGION` | — (필수) | Bedrock 리전 |
| `AWS_ACCESS_KEY_ID` | — | Access Key 경로. **`Settings`에 넣지 않는다** (아래 참조) |
| `AWS_SECRET_ACCESS_KEY` | — | 위와 같은 경로 · 같은 이유로 `Settings`에 넣지 않는다 |
| `SCOUT_MODEL_ID` | `anthropic.claude-sonnet-5` | 계정에 따라 형태가 다르다 — [07-검증](07-검증.md) M0 1번 |
| `SCOUT_RUNS_DIR` | `runs` | 실행 산출물 디렉터리 |
| `SCOUT_MAX_COMPONENTS` | `3` | `search`로 통과시킬 요소 수 |
| `SCOUT_MAX_CANDIDATES` | `3` | 요소당 후보 수 |
| `SCOUT_INTERVIEW_MAX_TURNS` | `5` | 되묻기 상한. 개발 중엔 `2`로 내린다 |
| `SCOUT_DESIGN_RECURSION_LIMIT` | `10` | `design` 툴 루프 상한 — **superstep 수**(툴 호출 4~5회) |
| `SCOUT_SEARCH_RECURSION_LIMIT` | `16` | `search` 툴 루프 상한 — 결정 지점당 |
| `SCOUT_DESIGN_WEB_SEARCHES` | `3` | 승인되는 웹검색 — `design`은 **실행 전체** |
| `SCOUT_SEARCH_WEB_SEARCHES` | `5` | 승인되는 웹검색 — `search`는 **결정 지점당** |
| `SCOUT_LLM_CACHE` | `false` | **개발용** LLM 응답 캐시. 아래 참조 |
| `SCOUT_LLM_CACHE_PATH` | `runs/llm-cache.sqlite` | 캐시 파일 |
| `SCOUT_LLM_CONCURRENCY` | `4` | LLM 동시 호출 상한. `doctor`가 이 값만큼 병렬 호출해 동시 쿼터를 확인한다 |
| `SCOUT_MCP_CONCURRENCY` | `8` | MCP 툴 동시 호출 상한 |
| `SCOUT_BEDROCK_READ_TIMEOUT_SECONDS` | `600` | Bedrock 읽기 상한. **하한 30** |
| `SCOUT_BEDROCK_CONNECT_TIMEOUT_SECONDS` | `10` | 연결 상한. **하한 1** |
| `SCOUT_BEDROCK_MAX_ATTEMPTS` | `3` | 재시도 횟수. 1이면 재시도 없음. **1~10** |
| `SCOUT_MCP_READ_TIMEOUT_SECONDS` | `60` | MCP stdio 세션의 응답 대기 상한. **하한 5** |
| `SCOUT_MAX_SEARCH_REJECTIONS` | `3` | 거부 몇 번에 웹검색을 차단할지. **하한 1** |
| `SCOUT_MAX_REGROUND` | `1` | grounding 위반 시 재판정 횟수. 0이어도 **검출은 남는다**. **0~3** |
| `SCOUT_MAX_WEB_FACTS` | `6` | 후보당 dossier의 웹 사실 상한 = judge 프롬프트 크기. **하한 1** |
| `SCOUT_TOOL_PAYLOAD_CHARS` | `1200` | 에이전트 기록에서 툴 응답 하나를 자르는 길이. **하한 200** |
| `SCOUT_MIN_ALTERNATIVES` | `2` | 결정 지점의 최소 보기 수 (불변식 18). **하한 2 — 아래 참조** |
| `SCOUT_DECISIVE_GAP` | `2` | 1·2위 overall 차이가 이만큼이면 decisive. **1~4** |
| `SCOUT_REPORT_TITLE_CHARS` | `60` | 제목 상한. 넘으면 원문으로 폴백. **하한 40** |
| `SCOUT_REPORT_SUMMARY_CHARS` | `90` | 접힌 블록의 요약 줄 길이. **하한 30** |
| `SCOUT_REPORT_RISKS` | `3` | "가장 큰 위험"에 싣는 개수. **하한 1** |

`SCOUT_LOG_LEVEL`은 걷어냈다 — 아무도 읽지 않는 죽은 설정이었다. 동작하지 않는
손잡이를 이 목록에 두면 그게 거짓이 된다.

### ★ 범위 밖 값은 시작할 때 터진다

굵게 표시한 하한·상한은 Pydantic 필드 제약이다. 범위를 벗어나면 `Settings` 생성이
실패하고 `cli.py`가 `[FAIL] Settings 로딩 실패`로 이유까지 찍는다.

```
$ SCOUT_MIN_ALTERNATIVES=1 uv run scout doctor
[FAIL] Settings 로딩 실패 — 필수 변수(AWS_DEFAULT_REGION 등)를 확인하세요:
scout_min_alternatives
  Input should be greater than or equal to 2
```

조용히 무시하는 클램프(`max(2, 설정)`)를 쓰지 않는다 — **설정 파일에 적은 값과 실제
동작이 다른 것**이 가장 찾기 어려운 버그다. `SCOUT_MIN_ALTERNATIVES`의 하한 2는
불변식 18을 지킨다: 1이면 "무엇을 고를 것인가"에 답이 하나인 지점이 조사로 가고,
`search`가 억지 후보를 만들어 질문에 답하지 않는 후보가 1위로 올라온다(실측).
3·4로 올려 조이는 것은 정당한 조절이라 상한은 없다.

### ★ 설정을 값으로 읽지 않고 인자로 넘긴다

새 설정을 쓰는 함수는 값을 **인자로 받는다**(`wrap_web_search(..., budget=...)` 패턴).
노드가 `Settings`를 읽어 넘기고, 기본값은 모듈 상수로 둔다.

모듈 상수를 함수가 직접 읽으면 개발자 로컬 `.env`가 테스트 결과를 바꾼다 —
`.env`는 커밋되지 않으므로(불변식 10) **CI는 통과하는데 로컬만 깨지고 재현도 안 되는**
종류의 실패가 된다.

## MCP 서버(`scout-net-mcp`) 전용

앱은 이 값들을 쓰지 않는다. 서버가 자기 `Settings` 클래스로 읽는다.

| 변수 | 기본 | 설명 |
|---|---|---|
| `GITHUB_TOKEN` | — | 없으면 60req/h, 있으면 5000 |
| `SCOUT_EGRESS_ALLOWLIST` | 아래 6개 호스트 (쉼표 구분) | allowlist 밖은 거부 |
| `SCOUT_CACHE_DIR` | `.cache/scout-net` | 디스크 캐시 위치 |
| `SCOUT_CACHE_TTL_HOURS` | `24` | 캐시 유효 시간 |
| `SCOUT_RATE_LIMIT_RPS` | `5` | 토큰버킷 초당 요청. 버스트 허용량도 이 값이다(1초분) |
| `SCOUT_SEARCH_PROVIDER` | `ddg` | **교체 지점** — 사내 검색이 생기면 이 값만 바꾼다 |
| `SCOUT_NET_HTTP_TIMEOUT_SECONDS` | `10.0` | provider가 인터넷을 기다리는 상한. **0보다 커야 한다** |
| `SCOUT_NET_NPM_SEARCH_SIZE` | `10` | npm 검색이 받아올 목록 폭. **1~250** |

기본 allowlist:
`registry.npmjs.org` · `api.npmjs.org` · `pypi.org` · `api.github.com` · `api.osv.dev` · `www.google.com`

마지막 호스트가 `www.google.com`인 것은 `ddgs`가 backend를 `google`로 고정했을 때
실제로 때리는 곳이기 때문이다 — 품질 비교로 고른 검색엔진이고 duckduckgo가 아니다
(`providers/search.py`).

`SCOUT_NET_HTTP_TIMEOUT_SECONDS`의 기본 10초가 짧다는 것은 이미 관측됐다 — 웹검색
승인 프롬프트가 떠 있는 동안 다른 결정 지점의 in-flight 요청이 이 값에서 죽는다
([09-출력양식](09-출력양식.md) · [CHANGELOG v29](CHANGELOG.md)). 재시도는 없다 —
실패는 `gaps`에 기록하고 계속한다(불변식 11).

### ★ 새 서버 설정은 `SCOUT_NET_` 접두사를 쓴다

`SERVER_ENV_KEYS`(아래) 화이트리스트를 통과하지 못한 이름은 **자식 프로세스에 도달하지
않고 조용히 기본값이 쓰인다.** 증상이 "환경변수가 안 먹는다"로만 보이는 함정이라,
`test_egress`가 서버 `Settings`의 모든 필드가 화이트리스트를 통과하는지 검사한다.

## `SCOUT_MODEL_ID` — 배선 검증과 판단 검증은 다른 모델로 본다

**정본은 Sonnet이다.** 설계와 프롬프트 앵커가 그 모델을 전제하고, 검증 기준도 거기서
본다. 작은 모델(Haiku)은 **Bedrock 일일 토큰 쿼터에 걸릴 때 임시로** 쓴다 —
파이프라인 배선을 확인하는 데는 그걸로 충분하기 때문이다.

둘을 섞은 채 결과를 보면 "왜 그때는 걸러내기가 안 됐지"에서 헤매므로, 무엇을 볼 수
있고 무엇을 볼 수 없는지 적어둔다.

| 용도 | 모델 | 무엇을 볼 수 있나 |
|---|---|---|
| **배선 검증** | 작은 모델도 된다 (쿼터 회피용 임시) | 단계 연결 · 저장 · 렌더링 · 실패 경로 · 테이블이 채워지는지 |
| **판단 검증** | **Sonnet** (정본) | [07-검증](07-검증.md) 성공 기준 7 · 8-1 · 8-2 · 9 · 9-1의 육안 확인 |

### 작은 모델에서 실측된 흔들림 세 가지

파이프라인이 이걸 견디도록 만들어져 있다 — 형식은 흡수하고, **판단은 흡수하지 않는다.**

| 증상 | 성격 | 어디가 받아내는가 |
|---|---|---|
| 한 객체를 `tool_use` 두 블록으로 쪼갬 (`architecture` / `components`) | 도구 호출 형식 | `llm.py`의 `_salvage` — args를 병합해 검증 |
| 리스트 자리에 의사 XML 문자열 (`<item>…`, `<parameter name="pro">…`) | 직렬화 형식 | `schemas.py`의 `StrList` — 태그 경계로 쪼갠다 |
| `necessity`와 `needs_comparison`을 혼동 (걸러내기가 0개) | **판단 품질** | **흡수하지 않는다.** `design`이 `gaps`에 기록하고 넘어간다 |

앞의 둘은 어느 모델에서도 날 수 있는 형식 문제이고, 흡수하지 않으면 형식 흔들림 하나가
후보를 통째로 탈락시켜 조사 결과를 지운다. 세 번째는 다르다 — 여기서 프롬프트를 작은
모델에 맞춰 휘면 `necessity`의 이중 축(이 도구의 차별점)이 모델에 종속되고, 정본
모델로 돌아왔을 때 그 왜곡이 남는다.
**걸러내기가 0개로 나오면 프롬프트를 고치기 전에 모델을 먼저 본다.**

## 개발용 LLM 캐시 — `SCOUT_LLM_CACHE`

한 번 돌리면 LLM 호출이 기본값에서 40회쯤이고, ReAct는 스텝마다 이전 메시지 전체를
다시 보내므로 프롬프트와 무관한 반복(렌더링 확인·리팩터·뒤 단계만 고치기)에서도
일일 토큰 쿼터가 그대로 깎인다. `scout/llm_cache.py`가 그 반복 비용을 없앤다.

```
SCOUT_LLM_CACHE=1 uv run scout run "..." --stop-after design
   → 1회차: 캐시 적중 0 / 미스 6
SCOUT_LLM_CACHE=1 uv run scout run "..." --stop-after design
   → 2회차: 캐시 적중 6 / 미스 0     (Bedrock 호출 0)
```

`(프롬프트 문자열, llm_string)`을 키로 sqlite에 담는다. `llm_string`이 모델·파라미터·
**바인딩된 툴**을 인코딩하므로 툴셋이 다른 호출은 키가 저절로 갈린다.

### ★ 프롬프트를 고치면 그 단계만 자동으로 미스가 된다

키가 프롬프트 문자열이라 별도 무효화 장치가 필요 없다 — `DESIGN_EXTRACT_SYSTEM_PROMPT`에
앵커 한 줄을 추가하면 그 호출만 미스가 되고 나머지는 적중한다. 프롬프트 튜닝 반복에서
정확히 원하는 동작이다.

### 기본이 off인 이유 — 두 가지

1. **신선도가 이 도구의 값어치다.** 캐시가 켜진 채 실전 실행이 돌면 어제의 판정이
   오늘의 추천으로 나온다
2. **비결정성이 사라진다.** 같은 프롬프트+입력이면 같은 응답이라 judge 품질의 편차를
   볼 수 없다 — [07-검증](07-검증.md)의 성공 기준 7·8-1·9·9-1은 **캐시를 끄고**
   확인한다

`doctor`에는 걸지 않는다 — 실측이 목적인 명령이다.
MCP 서버의 디스크 캐시(24h TTL)와는 다른 층이다: 그쪽은 HTTP 응답, 이쪽은 LLM 응답이다.

## ★ AWS 변수는 표준 이름을 쓴다 — boto3에 맡긴다

`langchain-aws` `ChatBedrockConverse`는 내부적으로 boto3를 쓴다.
boto3는 표준 변수를 **자기 자격 체인으로 알아서 집는다.**

| 변수 | 누가 읽는가 |
|---|---|
| `AWS_DEFAULT_REGION` | boto3 + 우리 `Settings`(명시 전달용) |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | **boto3만** |

### 규칙 1 — AWS 변수에 `SCOUT_` 접두사를 붙이지 않는다

`SCOUT_AWS_REGION` 같은 이름을 만들면 boto3의 기본 동작이 깨지고 우리가 손으로 배선해야 한다.
표준 이름을 그대로 쓴다. `SCOUT_` 접두사는 **우리 앱 고유 설정에만** 쓴다.

### 규칙 2 — 크레덴셜을 `Settings`에 담지 않는다

`AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY`를 읽어서 넘기면 크레덴셜이 우리 객체 · 로그 ·
예외 트레이스에 들어올 수 있다. boto3가 환경에서 직접 집게 두고, `doctor`는 **존재 여부만**
확인한다.

```python
# doctor — 값은 찍지 않는다
has_key = bool(os.environ.get("AWS_ACCESS_KEY_ID")) and bool(os.environ.get("AWS_SECRET_ACCESS_KEY"))
print(f"AWS Access Key: {'설정됨' if has_key else '미설정'}")
```

```python
# llm.py — 크레덴셜을 통과시키지 않고 boto3에 맡긴다
ChatBedrockConverse(
    model=settings.model_id,          # SCOUT_MODEL_ID
    region_name=settings.aws_region,  # AWS_DEFAULT_REGION
)
```

**크레덴셜은 아무것도 명시 전달하지 않는다** — boto3 기본 체인이 `AWS_ACCESS_KEY_ID` ·
`AWS_SECRET_ACCESS_KEY`를 환경에서 알아서 집는다. **이게 표준 이름을 쓰는 실질 이득이다.**

리전 외에 넘기는 것은 `botocore.config.Config` 하나다 — 타임아웃·재시도다.

```python
config=Config(
    connect_timeout=settings.scout_bedrock_connect_timeout_seconds,
    read_timeout=settings.scout_bedrock_read_timeout_seconds,
    retries={"max_attempts": settings.scout_bedrock_max_attempts, "mode": "standard"},
)
```

`ChatBedrockConverse`에도 `timeout=`·`max_retries=` 인자가 있지만 쓰지 않는다 —
`timeout=`이 connect와 read를 **같은 값으로 묶고**, `max_retries=`는 `max_attempts`만
정해 retry mode를 못 바꾼다. 연결은 빠르거나 아예 안 되므로(느리면 리전·자격 문제다)
따로 잡아야 하고, mode는 `standard`여야 한다 — 기본 `legacy`는 `ThrottlingException`
처리가 좁고 `verify`가 후보를 병렬로 돌려 스로틀링에 부딪힌다. `adaptive`는 클라이언트
측 레이트리미팅이 붙어 우리 `Semaphore`와 이중이 된다.

이 값들은 크레덴셜이 아니므로 `Settings`에 담아도 규칙 2와 무관하고, `SCOUT_` 접두사를
쓰므로 규칙 1과도 무관하다 — boto3가 읽는 표준 변수가 아니라 우리가 넘기는 값이다.

`doctor`가 실제로 적용된 값을 찍는다:

```
[OK] 4병렬 호출 성공 (4개 응답, 동시 쿼터 확인됨)
      타임아웃: 연결 10s · 읽기 600s · 재시도 3회
```

인증 방식 확인은 [07-검증](07-검증.md)의 M0 항목이다.

## 로딩 — `pydantic-settings`

`config.py`를 `BaseSettings` 서브클래스로 만든다. 이미 `pydantic`을 쓰므로 자연스럽다.

```python
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    aws_region: str = Field(validation_alias="AWS_DEFAULT_REGION")  # 필수
    # AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY 는 여기 없다 (규칙 2)

    scout_model_id: str = "anthropic.claude-sonnet-5"
    scout_runs_dir: str = "runs"
    scout_max_components: int = 3
    scout_max_candidates: int = 3
    scout_llm_concurrency: int = 4
    scout_mcp_concurrency: int = 8
    scout_log_level: str = "info"
```

얻는 것:

- **타입 검증이 공짜다** — `SCOUT_MAX_COMPONENTS=abc` 를 시작 시 잡는다
- **기본값이 한 곳에 모인다**
- **필수 변수 누락을 실행 전에 잡는다** — `AWS_DEFAULT_REGION`이 없으면 즉시 실패한다.
  `doctor`가 이걸 검증한다
- `Settings` 필드는 `env_file` 로딩이 내장이라 그 자체로는 `python-dotenv`가 따로 필요 없다

### ★ `boto3`는 `.env`를 모른다

`pydantic-settings`의 `env_file` 로딩은 **`Settings` 필드에만** 값을 채운다 — `os.environ`
자체는 건드리지 않는다. 그런데 `AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY`는 규칙 2에 따라
`Settings` 필드가 아니고, `boto3`는 `.env` 파일의 존재조차 모른 채 **오직 `os.environ`만** 읽는다.
그대로 두면 `.env`에 값을 채워도 `boto3`가 찾지 못한다.

그래서 `python-dotenv`의 `load_dotenv()`로 `.env`를 프로세스 환경에 명시적으로 올린다 —
CLI 진입점(`scout/cli.py`의 `@app.callback()`)에서 어떤 서브커맨드든 시작 전에 한 번 호출한다.
이건 위 항목과 모순이 아니다: `Settings` 필드 값은 `env_file` 로딩만으로 충분하고,
**boto3처럼 `Settings`를 거치지 않는 라이브러리**를 위해 `load_dotenv()`가 필요하다.

MCP 서버는 **자기 `Settings` 클래스를 따로 갖는다.** 앱 것을 import하지 않는다 —
워크스페이스 경계([05-프로젝트관리](05-프로젝트관리.md))를 코드에서도 지킨다.

### 우선순위

```
CLI 플래그   >   환경변수 / .env   >   Settings 기본값
```

`--max-components 8` 이 `SCOUT_MAX_COMPONENTS=3` 을 덮는다.

## ★ 크레덴셜 경계를 stdio에서 강제하는 방법

`GITHUB_TOKEN`은 MCP 서버 쪽에만 둔다([04-아키텍처](04-아키텍처.md)).
그런데 **stdio는 부모 프로세스의 환경을 자식이 물려받는다** — 그냥 두면 경계가 없다.

`MultiServerMCPClient`의 stdio 설정에 `env`를 **명시적으로 지정**해 통과할 변수만 남긴다.

```python
# mcp_client.py
SERVER_ENV_KEYS = ("GITHUB_TOKEN", "SCOUT_EGRESS_", "SCOUT_CACHE_",
                   "SCOUT_RATE_", "SCOUT_SEARCH_PROVIDER", "SCOUT_NET_",
                   # 크레덴셜이 아니라 Windows에서 자식 프로세스가 뜨는 데 필요한 값
                   "PATH", "SystemRoot")

server_env = {
    k: v for k, v in os.environ.items()
    if any(k == p or k.startswith(p) for p in SERVER_ENV_KEYS)
}
# → MCP 서버 프로세스에 AWS_* 가 존재하지 않는다
```

### 정직한 한계

앱 프로세스는 `.env` 전체를 읽으므로 `GITHUB_TOKEN`을 **메모리에 갖는다.**

- **stdio에서는 경계가 논리적이다** — 서버가 AWS 자격을 못 보는 것까지가 얻는 선
- **streamable-http로 바꾸면 물리적이 된다** — 서버가 별도 호스트에서 자기 `.env`를 읽고,
  앱은 `GITHUB_TOKEN`을 아예 모른다

001의 "전송 전환은 FastMCP에서 한 줄"에 이 이득이 딸려 온다.
사내 DMZ 배포가 곧 이 전환이다.

## `.env.example`

**전문을 여기 옮겨 적지 않는다.** 루트의
[`.env.example`](../../.env.example)이 그 파일이고, 위 표가 항목의 정본이다.

전문을 두 곳에 두면 갈린다 — 실제로 그랬다. v22가 설정 4개를 코드 상수에서 `Settings`로
내렸는데 이 문서의 예시 블록만 갱신되지 않아, 사용자는 `.env.example`을 보고 그
설정이 존재하는지조차 몰랐다. 옮긴 목적이 절반만 달성된 상태로 남았다.

그래서 이 문서가 지는 것은 **표(항목·기본값·범위·이유)**이고, 붙여 쓸 파일은
`.env.example`이다. 새 설정을 만들면 둘 다 고친다.
