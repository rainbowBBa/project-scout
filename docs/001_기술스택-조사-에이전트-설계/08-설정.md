# 08 · 설정과 환경변수

← [문서 목록](README.md)

설정은 `.env` 하나에 모으고 `pydantic-settings`로 읽는다.
이 파일이 **설정 항목의 단일 목록**이다 — 다른 문서에 흩어져 있던 값을 여기 모았다.

## 앱(`scout`) 전용

MCP 서버 프로세스에는 넘기지 않는다.

| 변수 | 기본 | 설명 |
|---|---|---|
| `AWS_DEFAULT_REGION` | — (필수) | Bedrock 리전 |
| `AWS_ACCESS_KEY_ID` | — | Access Key 경로. **`Settings`에 넣지 않는다** (아래 참조) |
| `AWS_SECRET_ACCESS_KEY` | — | 위와 같은 경로 · 같은 이유로 `Settings`에 넣지 않는다 |
| `SCOUT_MODEL_ID` | `anthropic.claude-sonnet-5` | 계정에 따라 형태가 다르다 — [07-검증](07-검증.md) M0 1번 |
| `SCOUT_RUNS_DIR` | `runs` | 실행 산출물 디렉터리 |
| `SCOUT_MAX_COMPONENTS` | `3` | `search`로 통과시킬 요소 수 |
| `SCOUT_MAX_CANDIDATES` | `3` | 요소당 후보 수 |
| `SCOUT_INTERVIEW_MAX_TURNS` | `5` | 되묻기 상한. 개발 중엔 `2`로 내린다 |
| `SCOUT_DESIGN_RECURSION_LIMIT` | `10` | `design` 툴 루프 상한 — **superstep 수**(툴 호출 4~5회) |
| `SCOUT_SEARCH_RECURSION_LIMIT` | `16` | `search` 툴 루프 상한 — 결정 지점당 |
| `SCOUT_DESIGN_WEB_SEARCHES` | `3` | 승인되는 웹검색 — `design`은 **실행 전체** |
| `SCOUT_SEARCH_WEB_SEARCHES` | `5` | 승인되는 웹검색 — `search`는 **결정 지점당** |
| `SCOUT_LLM_CACHE` | `false` | **개발용** LLM 응답 캐시. 아래 참조 |
| `SCOUT_LLM_CACHE_PATH` | `runs/llm-cache.sqlite` | 캐시 파일 |
| `SCOUT_LLM_CONCURRENCY` | `4` | LLM 동시 호출 상한 |
| `SCOUT_MCP_CONCURRENCY` | `8` | MCP 툴 동시 호출 상한 |
| `SCOUT_LOG_LEVEL` | `info` | |

## MCP 서버(`scout-net-mcp`) 전용

앱은 이 값들을 쓰지 않는다. 서버가 자기 `Settings` 클래스로 읽는다.

| 변수 | 기본 | 설명 |
|---|---|---|
| `GITHUB_TOKEN` | — | 없으면 60req/h, 있으면 5000 |
| `SCOUT_EGRESS_ALLOWLIST` | 아래 6개 호스트 (쉼표 구분) | allowlist 밖은 거부 |
| `SCOUT_CACHE_DIR` | `.cache/scout-net` | 디스크 캐시 위치 |
| `SCOUT_CACHE_TTL_HOURS` | `24` | 캐시 유효 시간 |
| `SCOUT_RATE_LIMIT_RPS` | `5` | 토큰버킷 초당 요청 |
| `SCOUT_SEARCH_PROVIDER` | `ddg` | **교체 지점** — 사내 검색이 생기면 이 값만 바꾼다 |

기본 allowlist:
`registry.npmjs.org` · `api.npmjs.org` · `pypi.org` · `api.github.com` · `api.osv.dev` · `duckduckgo.com`

## 개발용 LLM 캐시 — `SCOUT_LLM_CACHE`

한 번 돌리면 LLM 호출이 기본값에서 40회쯤이고, ReAct는 스텝마다 이전 메시지 전체를
다시 보내므로 프롬프트와 무관한 반복(렌더링 확인·리팩터·뒤 단계만 고치기)에서도
일일 토큰 쿼터가 그대로 깎인다. `scout/llm_cache.py`가 그 반복 비용을 없앤다.

```
SCOUT_LLM_CACHE=1 uv run scout run "..." --stop-after design
   → 1회차: 캐시 적중 0 / 미스 6
SCOUT_LLM_CACHE=1 uv run scout run "..." --stop-after design
   → 2회차: 캐시 적중 6 / 미스 0     (Bedrock 호출 0)
```

`(프롬프트 문자열, llm_string)`을 키로 sqlite에 담는다. `llm_string`이 모델·파라미터·
**바인딩된 툴**을 인코딩하므로 툴셋이 다른 호출은 키가 저절로 갈린다.

### ★ 프롬프트를 고치면 그 단계만 자동으로 미스가 된다

키가 프롬프트 문자열이라 별도 무효화 장치가 필요 없다 — `DESIGN_EXTRACT_SYSTEM_PROMPT`에
앵커 한 줄을 추가하면 그 호출만 미스가 되고 나머지는 적중한다. 프롬프트 튜닝 반복에서
정확히 원하는 동작이다.

### 기본이 off인 이유 — 두 가지

1. **신선도가 이 도구의 값어치다.** 캐시가 켜진 채 실전 실행이 돌면 어제의 판정이
   오늘의 추천으로 나온다
2. **비결정성이 사라진다.** 같은 프롬프트+입력이면 같은 응답이라 judge 품질의 편차를
   볼 수 없다 — [07-검증](07-검증.md)의 성공 기준 7·8-1·9·9-1은 **캐시를 끄고**
   확인한다

`doctor`에는 걸지 않는다 — 실측이 목적인 명령이다.
MCP 서버의 디스크 캐시(24h TTL)와는 다른 층이다: 그쪽은 HTTP 응답, 이쪽은 LLM 응답이다.

## ★ AWS 변수는 표준 이름을 쓴다 — boto3에 맡긴다

`langchain-aws` `ChatBedrockConverse`는 내부적으로 boto3를 쓴다.
boto3는 표준 변수를 **자기 자격 체인으로 알아서 집는다.**

| 변수 | 누가 읽는가 |
|---|---|
| `AWS_DEFAULT_REGION` | boto3 + 우리 `Settings`(명시 전달용) |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | **boto3만** |

### 규칙 1 — AWS 변수에 `SCOUT_` 접두사를 붙이지 않는다

`SCOUT_AWS_REGION` 같은 이름을 만들면 boto3의 기본 동작이 깨지고 우리가 손으로 배선해야 한다.
표준 이름을 그대로 쓴다. `SCOUT_` 접두사는 **우리 앱 고유 설정에만** 쓴다.

### 규칙 2 — 크레덴셜을 `Settings`에 담지 않는다

`AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY`를 읽어서 넘기면 크레덴셜이 우리 객체 · 로그 ·
예외 트레이스에 들어올 수 있다. boto3가 환경에서 직접 집게 두고, `doctor`는 **존재 여부만**
확인한다.

```python
# doctor — 값은 찍지 않는다
has_key = bool(os.environ.get("AWS_ACCESS_KEY_ID")) and bool(os.environ.get("AWS_SECRET_ACCESS_KEY"))
print(f"AWS Access Key: {'설정됨' if has_key else '미설정'}")
```

```python
# llm.py — 크레덴셜을 통과시키지 않고 boto3에 맡긴다
ChatBedrockConverse(
    model=settings.model_id,          # SCOUT_MODEL_ID
    region_name=settings.aws_region,  # AWS_DEFAULT_REGION
)
```

리전 외에는 아무것도 명시 전달하지 않는다 — boto3 기본 체인이 `AWS_ACCESS_KEY_ID` ·
`AWS_SECRET_ACCESS_KEY`를 환경에서 알아서 집는다. **이게 표준 이름을 쓰는 실질 이득이다.**

인증 방식 확인은 [07-검증](07-검증.md)의 M0 항목이다.

## 로딩 — `pydantic-settings`

`config.py`를 `BaseSettings` 서브클래스로 만든다. 이미 `pydantic`을 쓰므로 자연스럽다.

```python
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    aws_region: str = Field(validation_alias="AWS_DEFAULT_REGION")  # 필수
    # AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY 는 여기 없다 (규칙 2)

    scout_model_id: str = "anthropic.claude-sonnet-5"
    scout_runs_dir: str = "runs"
    scout_max_components: int = 3
    scout_max_candidates: int = 3
    scout_llm_concurrency: int = 4
    scout_mcp_concurrency: int = 8
    scout_log_level: str = "info"
```

얻는 것:

- **타입 검증이 공짜다** — `SCOUT_MAX_COMPONENTS=abc` 를 시작 시 잡는다
- **기본값이 한 곳에 모인다**
- **필수 변수 누락을 실행 전에 잡는다** — `AWS_DEFAULT_REGION`이 없으면 즉시 실패한다.
  `doctor`가 이걸 검증한다
- `Settings` 필드는 `env_file` 로딩이 내장이라 그 자체로는 `python-dotenv`가 따로 필요 없다

### ★ `boto3`는 `.env`를 모른다

`pydantic-settings`의 `env_file` 로딩은 **`Settings` 필드에만** 값을 채운다 — `os.environ`
자체는 건드리지 않는다. 그런데 `AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY`는 규칙 2에 따라
`Settings` 필드가 아니고, `boto3`는 `.env` 파일의 존재조차 모른 채 **오직 `os.environ`만** 읽는다.
그대로 두면 `.env`에 값을 채워도 `boto3`가 찾지 못한다.

그래서 `python-dotenv`의 `load_dotenv()`로 `.env`를 프로세스 환경에 명시적으로 올린다 —
CLI 진입점(`scout/cli.py`의 `@app.callback()`)에서 어떤 서브커맨드든 시작 전에 한 번 호출한다.
이건 위 항목과 모순이 아니다: `Settings` 필드 값은 `env_file` 로딩만으로 충분하고,
**boto3처럼 `Settings`를 거치지 않는 라이브러리**를 위해 `load_dotenv()`가 필요하다.

MCP 서버는 **자기 `Settings` 클래스를 따로 갖는다.** 앱 것을 import하지 않는다 —
워크스페이스 경계([05-프로젝트관리](05-프로젝트관리.md))를 코드에서도 지킨다.

### 우선순위

```
CLI 플래그   >   환경변수 / .env   >   Settings 기본값
```

`--max-components 8` 이 `SCOUT_MAX_COMPONENTS=3` 을 덮는다.

## ★ 크레덴셜 경계를 stdio에서 강제하는 방법

`GITHUB_TOKEN`은 MCP 서버 쪽에만 둔다([04-아키텍처](04-아키텍처.md)).
그런데 **stdio는 부모 프로세스의 환경을 자식이 물려받는다** — 그냥 두면 경계가 없다.

`MultiServerMCPClient`의 stdio 설정에 `env`를 **명시적으로 지정**해 통과할 변수만 남긴다.

```python
# mcp_client.py
SERVER_ENV_KEYS = ("GITHUB_TOKEN", "SCOUT_EGRESS_", "SCOUT_CACHE_",
                   "SCOUT_RATE_", "SCOUT_SEARCH_PROVIDER")

server_env = {
    k: v for k, v in os.environ.items()
    if any(k == p or k.startswith(p) for p in SERVER_ENV_KEYS)
}
# → MCP 서버 프로세스에 AWS_* 가 존재하지 않는다
```

### 정직한 한계

앱 프로세스는 `.env` 전체를 읽으므로 `GITHUB_TOKEN`을 **메모리에 갖는다.**

- **stdio에서는 경계가 논리적이다** — 서버가 AWS 자격을 못 보는 것까지가 얻는 선
- **streamable-http로 바꾸면 물리적이 된다** — 서버가 별도 호스트에서 자기 `.env`를 읽고,
  앱은 `GITHUB_TOKEN`을 아예 모른다

001의 "전송 전환은 FastMCP에서 한 줄"에 이 이득이 딸려 온다.
사내 DMZ 배포가 곧 이 전환이다.

## `.env.example`

```bash
# ─────────────────────────────────────────────────────────────
# 앱(scout) — MCP 서버에 넘기지 않는다
# ─────────────────────────────────────────────────────────────

# Bedrock 리전 (필수)
AWS_DEFAULT_REGION=us-east-1

# 인증 — Access Key 방식. boto3가 환경에서 직접 읽는다. Settings에는 들어가지 않는다
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=

# 모델 ID — 계정에 따라 형태가 다르다. scout doctor 가 찍어준다
#   anthropic.claude-sonnet-5 | us.anthropic.claude-sonnet-5 | arn:aws:bedrock:...
SCOUT_MODEL_ID=anthropic.claude-sonnet-5

# 규모 (CLI 플래그가 이 값을 덮는다)
SCOUT_MAX_COMPONENTS=3
SCOUT_MAX_CANDIDATES=3

# 동시성
SCOUT_LLM_CONCURRENCY=4
SCOUT_MCP_CONCURRENCY=8

SCOUT_RUNS_DIR=runs
SCOUT_LOG_LEVEL=info

# ─────────────────────────────────────────────────────────────
# MCP 서버(scout-net-mcp) — 앱은 읽지 않고 그대로 전달만 한다
# ─────────────────────────────────────────────────────────────

# 없으면 60req/h. 프로토타입 규모(후보 8~10개)면 1회는 되지만 반복하면 소진된다
GITHUB_TOKEN=

# allowlist 밖 도메인은 거부되고 감사 로그에 남는다
SCOUT_EGRESS_ALLOWLIST=registry.npmjs.org,api.npmjs.org,pypi.org,api.github.com,api.osv.dev,duckduckgo.com

SCOUT_CACHE_DIR=.cache/scout-net
SCOUT_CACHE_TTL_HOURS=24
SCOUT_RATE_LIMIT_RPS=5

# 교체 지점 — 사내 검색 API가 생기면 이 값만 바꾼다
SCOUT_SEARCH_PROVIDER=ddg
```
