## 파일 안내

### [01-개요.md](01-개요.md)

이 도구를 왜 만드는지. **핵심 가설**("판정에 쓸 사실을 먼저 모아서 주면 LLM의 판단이 실제로
달라지는가")과 설계의 세 축(강제 인터뷰 · 닫힌 사실 집합 · 인용 검증). 문서 전체에서 쓰는
**용어 정의** — 요소 / 후보 / dossier / 사실 / 판정 / grounding.

> `dossier`가 무슨 뜻인지 모르겠으면 여기부터.

### [02-파이프라인.md](02-파이프라인.md)

6단계가 무엇이고 어떤 순서로 도는지. `scout run` 한 줄을 쳤을 때 화면에 무엇이 찍히는지
실행 예시로 보여준다. 단계별 세부는 다루지 않는다 — 그건 `stages/`.

### [03-저장.md](03-저장.md)

`runs/<slug>/scout.db` 하나에 담는 10개 테이블 스키마. **grounding 검증 SQL**의 본체가 여기
있다. `scout show`가 어떻게 동작하는지, 사람이 결과를 어떻게 열어보는지.

### [04-아키텍처.md](04-아키텍처.md)

프로세스 구성 — 본체(`scout`)와 인터넷 출구(`scout-net-mcp`)의 분리. Bedrock에서 쓸 수 있는
것과 못 쓰는 것, 그 제약이 설계를 어떻게 바꿨는지. **MCP 툴 6종** 명세.

### [05-프로젝트관리.md](05-프로젝트관리.md)

uv 워크스페이스가 **보안 경계를 의존성 수준에서 강제하는** 방식. ruff `TID251`로 인터넷 격리를
자동 검사하는 설정. ty를 게이트로 쓰지 않는 이유. 전체 디렉터리 구조와 명령 4개.

### [08-설정.md](08-설정.md)

`.env` 전문과 설정 항목 **단일 목록**. AWS 변수를 표준 이름으로 쓰고 크레덴셜을 `Settings`에
담지 않는 이유. **stdio에서 크레덴셜 경계를 강제하는 방법**(자식 프로세스 `env` 필터).
`.gitignore`.

> 환경 세팅을 시작하기 전에 여기부터.

### [06-범위와일정.md](06-범위와일정.md)

## 한 장으로 보는 전체 그림

```
사용자 ─▶ scout (본체)  ──────▶ AWS Bedrock (claude-sonnet-5)
                │
                └── stdio ──▶ scout-net-mcp ──▶ 인터넷
                              (유일한 출구)      npm / PyPI / GitHub
                                                OSV / DuckDuckGo

interview → design → search → verify → evaluate → report
   ↓          ↓        ↓         ↓         ↓          ↓
 runs     designs   candidates verdicts  scores   report.html
        components    facts    citations  picks
                      gaps            final_designs
                        └──────── runs/<slug>/scout.db ────────┘
```

**설계의 한 문장**: judge는 코드가 먼저 모아둔 사실만 인용할 수 있고,
그 인용이 실제로 존재하는지 코드가 다시 대조한다.

**답의 한 문장**: 사용자가 받는 것은 후보 목록이 아니라 **이렇게 만들면 되겠다는 설계**다.
