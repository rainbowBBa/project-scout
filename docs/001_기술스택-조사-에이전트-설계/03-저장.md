# 03 · 저장

← [문서 목록](README.md)

산출물을 단계별 JSON 파일이 아니라 **`runs/<slug>/scout.db` 하나**에 담는다.
`sqlite3`는 파이썬 표준 라이브러리라 의존성이 늘지 않고, LangGraph 체크포인터가 이미
SQLite를 쓰므로 저장 방식이 하나로 통일된다. ORM은 쓰지 않는다.

```
runs/<slug>/
├── scout.db            ★ 산출물 전부 (10개 테이블)
├── report.html
└── checkpoints.sqlite  LangGraph 체크포인터 (별도 파일)
```

---

## 파일이지 `:memory:`가 아니다

코드 차이는 연결 문자열 하나뿐이지만, 이유는 **개발 반복 속도**다.

dossier 수집이 가장 비싼 단계다 — 후보 10개 × MCP 호출 4~5회 + LLM 질의생성·랭킹.
Day 2 오후에 `verify` 프롬프트를 20번쯤 고칠 텐데, 인메모리면 매번 처음부터 다시 모으고
파일이면 `--from verify`로 바로 들어간다.

부수적으로, 인메모리 sqlite는 커넥션을 프로세스 내내 살려둬야 하고(닫으면 DB가 소멸)
asyncio에서 커넥션 공유 제약이 있다. 파일이 오히려 **덜** 복잡하다.

---

## 스키마

```sql
runs       (slug PK, description, created_at, interview_json)
           -- interview_json: refined_brief · assumptions (0-interview.md)

designs    (slug PK, summary, shape, data_flow, build_order_json, open_questions_json)
           -- design 단계의 Architecture 본문. slug당 1행 (1-design.md)

components (slug, name, kind, role_in_design, decision_question, alternatives_json,
            constraints_json, needs_comparison, no_comparison_reason,
            necessity, necessity_reason, priority, approach_notes, search_hints_json,
            PRIMARY KEY (slug, name))
           -- priority:         search 통과 상위 N개 정렬 기준
           -- alternatives:     실제로 고를 보기. 2개 미만이면 결정 지점이 아니다
           --                   → 코드가 needs_comparison=false로 내린다 (1-design.md)
           -- needs_comparison: false면 설계에서 이미 닫힌 결정 — search에 안 간다
           -- search_hints:     영어 기술 어휘. search의 질의 씨드 (1-design.md)

candidates (slug, component, name, kind, what_it_is,
            PRIMARY KEY (slug, component, name))

facts      (slug, candidate, fact_id, label, value, url, retrieved_at,
            PRIMARY KEY (slug, candidate, fact_id))     -- ★ dossier 본체

gaps       (slug, candidate, note)                       -- 못 구한 항목

verdicts   (slug, candidate, solves_it, solves_reason, confidence,
            pros_json, cons_json, caveats_json, unsupported_claims_json,
            grounding_violations INTEGER,
            PRIMARY KEY (slug, candidate))

citations  (slug, candidate, fact_id)                    -- ★ judge가 인용한 것

scores     (slug, candidate, criterion, score, source, reason,
            -- criterion: maturity | risk | overall   (score는 NULL 가능)
            -- source:    computed  | judged | unavailable
            -- reason:    계산 근거 요약 또는 judge의 score_reason
            PRIMARY KEY (slug, candidate, criterion))

picks      (slug, component, candidate, rank, rejected_reason,
            winner_reason, runner_up_note, margin)
            -- margin: decisive | close   (1위 행에만)

final_designs (slug PK, summary, shape, data_flow, changes_from_design_json,
               stack_rationale, integration_notes_json, combination_risks_json,
               build_order_json, unresolved_json)
            -- evaluate가 designs를 조사 결과로 수정해 확정한 설계. slug당 1행
            -- shape·data_flow: designs와 같은 이름 — 같은 필드의 v2다 (4-evaluate.md)
```

### `designs`와 `final_designs`가 따로인 이유 — v1과 v2다

같은 slug에 설계가 두 번 저장된다. `final_designs`는 별개 문서가 아니라
**`designs`의 수정판**이다 — 그래서 `shape`·`data_flow`를 **같은 이름으로** 갖는다.

```
designs.shape        "단일 Node 백엔드가 실시간 연결과 요약 워커를 함께 처리"
                          │  socket.io 판정의 caveats 가 이 전제를 깨뜨렸다
                          ▼
final_designs.shape  "요약 워커를 별 프로세스로 분리"
final_designs.changes_from_design[0]  왜 바꿨는지 + 근거
```

한 테이블에 덮어쓰면 **"조사해보니 전제가 바뀌었다"가 사라진다.** 그게 이 도구가
값어치를 증명하는 지점이므로 두 버전을 남긴다. 보고서는 확정본을 최상단에,
기본틀을 `<details>`로 두어 같은 필드를 나란히 보여준다
([stages/5-report.md](stages/5-report.md)) — `report`는 LLM이 없으므로 차이를
문장으로 쓰지 않고 **나란히 놓기만** 한다.

`search_hints`도 같은 성격이다 — **상태로만 넘기지 않고 저장한다.**
`store.get_components`로 돌아오는 재실행 경로에서 힌트가 사라지면, `design`이 만든
효과가 재실행에서 소멸한다.

Pydantic 모델(`schemas.py`)은 그대로 유지한다 — LLM 구조화 출력용이다.
sqlite는 저장·조회용이고, 변환은 `model_dump()` / `model_validate()`.

### 리스트 필드를 JSON 컬럼에 넣는 기준

`pros` / `cons` / `caveats`는 `*_json` 컬럼에 그대로 담는다. **조회 조건으로 쓰지 않기 때문**이다.
반대로 `facts`와 `citations`는 조회·조인 대상이라 별도 테이블로 정규화했다.

## 이 선택이 만든 이득

### grounding 검증이 SQL 한 줄

```sql
SELECT c.candidate, c.fact_id
FROM citations c
LEFT JOIN facts f ON c.slug = f.slug
                 AND c.candidate = f.candidate
                 AND c.fact_id  = f.fact_id
WHERE c.slug = ? AND f.fact_id IS NULL;   -- ← dossier에 없는 id를 인용한 것
```

파이썬 집합 차집합보다 깔끔하다. 이 쿼리가 `grounding.py`의 본체다 —
전체 흐름은 [stages/3-verify.md](stages/3-verify.md).

### evaluate의 사실 조회가 자연스럽다

```sql
SELECT value FROM facts
WHERE slug = ? AND candidate = ? AND fact_id = 'npm.last_release';
```

`maturity` 점수 공식에 넣을 숫자를 이렇게 꺼낸다.
중첩 JSON을 파고드는 코드가 사라진다.

### 계산과 판단이 행마다 구분된다

`scores.source`가 세 값을 기록한다 — `computed`(코드 계산) / `judged`(judge 판단) /
`unavailable`(계산할 숫자가 없음). 보고서에서 어느 숫자가 사실 기반이고 어느 게 해석인지
배지로 구분해 표시한다.

`method` 후보는 레지스트리가 없어 `maturity`를 계산할 수 없는데, 이때 점수를 0으로 두면
실제보다 불리해 보인다. `NULL` + `unavailable`로 두면 **낮은 게 아니라 없는 것**이 된다.

`reason` 컬럼은 계산 점수의 근거 요약(`"npm.last_release 11일 전, 기여자 42명 → 5"`)과
judge의 `score_reason`을 같은 자리에 담는다. JSON 중첩 구조였다면 따로 설계해야 했다.

## 사람이 열어보는 경로

```
$ uv run scout show <slug> verify
```

해당 단계의 테이블을 JSON으로 덤프해 stdout에 낸다. 파일을 상시 만들지 않으므로 복잡도가
늘지 않는다. 손으로 고칠 일이 생기면 sqlite를 직접 `UPDATE`하는 게 JSON 편집보다 편하다
(DB Browser for SQLite 같은 GUI를 쓰면 더 빠르다).

| CLI 인자 | 덤프하는 테이블 |
|---|---|
| `interview` | `runs` |
| `design` | `designs` + `components` |
| `search` | `candidates` + `facts` + `gaps` |
| `verify` | `verdicts` + `citations` |
| `evaluate` | `scores` + `picks` + `final_designs` |

---

## ★ 재실행은 단계 산출물을 교체한다

각 단계가 쓰기 전에 **자기 산출물을 비운다** (`store.clear_stage_output(slug, stage)`).

| 단계 | 비우는 것 |
|---|---|
| `design` | `components`는 이미 DELETE + INSERT · 자기 단계명 gap |
| `search` | `candidates` · `facts` · 자기 단계명 gap + 후보·요소에 달린 gap |
| `verify` | `verdicts` · `citations` · 자기 단계명 gap |
| `evaluate` | `scores` · 자기 단계명 gap (`picks`는 요소별로 `clear_picks`) |

`designs`·`final_designs`는 slug당 1행이라 PK upsert로 충분하다.

### PK upsert만으로는 부족하다

`candidates`의 PK가 `(slug, component, name)`이라 같은 실행을 다시 돌리면 교체된다.
그런데 **`design`이 결정 지점 이름을 다르게 만들면** 이전 실행의 후보가 다른 키로
남아 고아가 된다. 실측:

```
'실시간 메시지 전달'      | socket.io | library     ← 이전 실행
'실시간 메시지 전달 계층'  | socket.io | library     ← 이후 실행
```

`evaluate`는 `store.get_candidates(slug)`를 읽으므로 **사라진 요소의 후보까지 계산
점수를 매긴다.** `components`는 원래 DELETE + INSERT였는데 나머지가 안 따라간 것이었다.

`gaps`는 `candidate` 컬럼이 후보명·요소명·단계명을 겸해서 단계별로 정확히 가를 수 없다.
각 단계는 자기 단계명 gap만 비우고, `search`가 자기가 다시 만들 후보·요소에 달린 gap을
함께 비운다. 전체 파이프라인을 다시 도는 정상 경로에서는 이걸로 충분하다.

---

## 스키마 마이그레이션은 없다

`store.py`는 `CREATE TABLE IF NOT EXISTS`만 실행한다. **기존 `scout.db`에 컬럼이
추가되지 않는다.** 프로토타입이라 마이그레이션 장치를 만들지 않았고, 스키마가 바뀌면
새 slug로 다시 돌린다 (`runs/<slug>/`를 지우거나 설명을 바꿔서).

컬럼이 바뀐 시점은 [CHANGELOG](CHANGELOG.md)에 남긴다 — 오래된 run 폴더를 열었다가
`no such column`을 보면 거기서 찾을 수 있어야 한다.
