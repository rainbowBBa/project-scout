## 테스트 6종

프로토타입이라 테스트를 6개만 남겼다. 여섯 다 **설계의 특정 주장이 사실인지 확인하는
역할**이고, 커버리지를 위한 게 아니다. 여섯 다 LLM을 부르지 않아 빠르고 결정론적이다.

| 테스트 | 검증하는 주장 | 없으면 |
|---|---|---|
| `test_grounding.py` | judge는 사실을 지어낼 수 없다 | LLM-as-judge를 신뢰할 근거가 없다 |
| `test_stale_regression.py` | 낡은 사실이 최종 추천을 바꾼다 | 이 도구의 존재 이유가 없다 |
| `test_necessity_wiring.py` | **걸러낸 결정 지점이 실제로 걸러진다** | 가장 차별적인 기능이 장식이 된다 |
| `test_egress.py` | 인터넷 출구가 실제로 통제된다 | 사내 보안 요구를 만족했다고 말할 수 없다 |
| `test_search_approval.py` | **거부하면 검색이 실제로 안 나간다** | 승인 UI가 장식이 된다 |
| `test_design_no_facts.py` | **`design`의 툴 결과는 dossier에 안 들어간다** | 설계 중에 스쳐본 값이 judge의 인용 대상이 된다 |

이 도구의 차별점은 둘이다 — **judge가 사실을 지어낼 수 없다**(grounding)와
**안 만들어도 되는 걸 알려준다**(`necessity`). 앞의 것만 테스트가 있으면 증거가 비대칭이다.
`test_necessity_wiring.py`가 그 비대칭을 없앤다.

### `test_grounding.py`

dossier에 없는 `fact_id`를 인용한 `Verdict`를 손으로 만들어 넣고, 검증기가 잡아내
`confidence`가 강등되는지 본다. LLM을 부르지 않으므로 빠르고 결정론적이다.

### `test_stale_regression.py`

아카이브된 패키지(예: `request`)를 후보로 주입한다. 최종 순위에서 탈락하고, 탈락 이유에
"마지막 릴리스" 사실이 인용되어야 한다.

judge가 낡은 사실을 무시해도 `evaluate`의 `maturity` 계산이 잡아내므로,
**판정과 계산 두 경로 중 하나만 작동해도 통과한다** — 그게 이중 안전망의 의미다.

### `test_necessity_wiring.py`

`design`이 걸러낸 결정 지점이 **실제로 걸러지는지** 본다.
`Design` 출력을 고정 픽스처로 주고 LLM 없이 코드 경로만 검사한다.

```
1. defer/unnecessary 결정 지점이 search 입력 목록에 들어가지 않는다
2. needs_comparison=false 인 것도 search 입력에 들어가지 않는다
3. 1번이 report 의 "지금 만들지 않아도 되는 것" 섹션에 렌더링된다
4. 2번이 report 의 "설계에서 이미 정해진 부분" 섹션에 렌더링된다
5. 걸러진 것이 0개면 경고가 출력된다
```

축이 둘인 이유는 [1-design.md](stages/1-design.md)에 있다 — **필요 없는 것**과
**이미 정해진 것**은 다르고, 둘 다 예산을 아끼면서 보고서에는 남아야 한다.

**LLM의 판단 품질은 결정론적으로 검증할 수 없다** — "전문검색이 정말 불필요한가"는
사람이 봐야 한다(성공 기준 7번). 대신 **배선**은 검증할 수 있다.
걸러놓고 `search`가 그냥 다 조사하면, 완료 기준 "최소 1개 걸러짐"은 통과하지만
기능은 아무 효과가 없다. 이 테스트가 그 경우를 잡는다.

`test_stale_regression.py`와 같은 성격이다 — **판단이 최종 결과를 실제로 바꾸는지.**

### `test_egress.py`

allowlist 밖 도메인 요청이 거부되고 감사 로그에 남는지 본다. 네트워크를 쓰지 않고
`egress.py`의 판정 함수를 직접 호출한다.

### `test_search_approval.py`

`test_necessity_wiring.py`와 같은 성격이다 — **배선**을 본다.
승인 문구만 띄우고 툴이 그냥 나가버리면 보안 기능이 장식이 된다. 원본 툴 대역을
넣고 호출 여부를 직접 확인한다.

```
1. 거부하면 원본 툴이 호출되지 않는다 (egress 0)
2. 거부 사유가 결과에 담겨 돌아온다 — 에이전트가 재질의할 재료
3. 승인하면 원본이 인자 그대로 호출된다
4. 거부가 반복되면 차단된다 (무한 재질의 방지)
5. 예산을 넘기면 검색이 안 나간다 / 거부는 예산을 깎지 않는다
6. 비대화형이면 프롬프트 없이 차단된다
7. `Fact.value`가 `ToolMessage` 원본에서 나오고, 무관한 후보에는 안 붙는다
```

7번이 `search`를 에이전트로 바꾸면서 생긴 새 위험을 막는다 — 사실이 LLM 문장에서
나오면 grounding은 통과하는데 내용은 환각인 상태가 된다.

### `test_design_no_facts.py`

`design`도 에이전트로 툴을 부르게 되면서 생긴 새 위험을 막는다.
`test_search_approval.py` 7번과 **같은 성격의 경계**를 반대편에서 지킨다.

```
1. design 단계가 툴을 불러도 facts 테이블에 행이 생기지 않는다
2. dossier 는 search 만 만든다 — design 이 부른 npm_package 의 값이
   candidates/facts 어디에도 나타나지 않는다
3. 통과 결정 지점의 search_hints 가 비면 gaps 에 기록된다
```

3번은 다른 두 개와 성격이 다르다 — 경계가 아니라 **이 단계를 만든 이유**를 지킨다.
`search_hints`가 비어도 파이프라인은 돌기 때문에(그게 `analyze` 시절의 상태였다)
조용히 원래대로 돌아가는 걸 막을 장치가 필요하다.

## 성공 기준

1. **E2E** — 다음 명령이 크래시 없이 완주하고, `scout.db`의 10개 테이블이 모두 채워지고
   `report.html`이 생성된다. `scout show <slug> verify`로 각 단계 결과를 확인할 수 있다.

   ```
   uv run scout run "AI 요약 기능이 있는 팀 채팅 앱, 3인 팀, TypeScript 숙련, 월 인프라 $200, 3개월"
   ```

2. **`test_grounding.py` 통과**

3. **`test_stale_regression.py` 통과**

4. **`test_necessity_wiring.py` 통과** — 걸러낸 요소가 `search`에 안 들어가고
   보고서에 나타난다. **배선의 증거**다

5. **`test_egress.py` 통과**

6. **인터넷 격리가 두 겹으로 확인됨** — `uv sync --package scout-net-mcp`가 langchain 없이
   성공하고, `uv run ruff check`가 `scout/`의 httpx/requests import를 `TID251`로 잡는다.
   손으로 grep하지 않는다.

6-1. **`test_search_approval.py` 통과 + 거부 루프 육안 확인** — 웹검색 승인 프롬프트에
   `n`을 주고 사유를 쓰면, **에이전트가 그 사유를 반영해 질의를 바꿔서** 다시 물어본다.
   같은 질의를 그대로 다시 물으면 거부 사유가 에이전트에 전달되지 않은 것이다.

   > 테스트가 잡는 건 "거부하면 egress가 0"이라는 **배선**이다.
   > 여기서 보는 건 **사유가 실제로 질의를 바꾸는가**다.

6-2. **`test_design_no_facts.py` 통과** — `design`이 툴을 불러도 dossier가 오염되지 않는다.
   불변식 4·13이 서 있는 자리를 지키는 **배선의 증거**다

7. **`design`의 걸러내기가 타당하다** (육안 확인) — `necessity`가 `unnecessary`/`defer`인
   요소가 0개가 아니고, **그 판단이 실제로 맞는지** 사람이 본다.
   위 예시 입력에서 "전문검색"이나 "파일 업로드"쯤은 걸러져야 한다.
   `necessity_reason`에 "200명"·"3인 팀" 같은 제약조건이 인용돼야 한다.

   > 배선은 `test_necessity_wiring.py`가 자동으로 잡는다.
   > 여기서 보는 건 **판단의 품질**이다 — essential인 걸 `unnecessary`로 잘못 분류하면
   > 테스트는 통과하지만 도구는 해롭다.

8. **`interview`가 구체화를 한다** — `refined_brief`가 원문 복사가 아니고, 대화에서
   나온 규모·예산·팀·데드라인·핵심 기능·범위 제외를 문장으로 담고 있다. 원문
   그대로면 구체화가 실패한 것이다

8-1. **`design`이 검색 가능한 어휘를 넘긴다** — 통과한 결정 지점의 `search_hints`가
   비어 있지 않고, **영어 기술 어휘**다. `["실시간 메시지 전달"]`처럼 요소 이름을
   그대로 복사한 것이면 실패다 — `npm_search`에 넣을 수 있는 값이어야 한다.

   > 이 기준이 이 단계를 `analyze`에서 `design`으로 재설계한 이유의 직접 확인이다
   > ([CHANGELOG v20](CHANGELOG.md)).

8-2. **`design`이 전제를 드러낸다** — `needs_comparison=false`가 최소 1개 나오고,
   `no_comparison_reason`이 `refined_brief`의 내용을 근거로 든다. 전부 `true`면
   프롬프트 반례가 안 먹힌 것이다.

9. **`evaluate`의 `winner_reason`에 제약조건이 인용된다** — "3인 팀", "3개월", "$200" 같은
   `refined_brief`의 값이 선정 이유에 등장해야 한다. 없으면 judge가 근거 없이 골랐다는 뜻이다

9-1. **확정 설계가 기본틀의 수정판이다** (육안 확인) — 이번 재설계의 핵심 확인이다.

   - `final_designs.shape`·`data_flow`가 **비어 있지 않다**. 확정 설계에 구조가
     없으면 "수정 설계 완성"이 성립하지 않는다
   - `changes_from_design`의 각 항목이 **조사 결과를 근거로 든다** —
     `verdicts`의 `cons`·`caveats` 또는 탈락 사유. "표현을 다듬었다" 같은 근거 없는
     재작성이면 실패다 (프롬프트 앵커가 안 먹힌 것)
   - 바꿀 근거가 없었으면 **`Architecture`를 그대로 유지**하고 변경 목록이 비어야
     한다. 그때 보고서에 "기본틀 유지"가 명시된다
   - `final_designs.summary`에 고른 후보 이름이 들어 있고, `integration_notes`가
     **두 선택이 만나는 지점**을 짚는다
   - `combination_risks`가 `verdicts.cons`의 사본이면 실패다 — 조합해서 비로소
     생기는 위험만 담겨야 한다 ([stages/4-evaluate.md](stages/4-evaluate.md))

10. **`report.html`이 브라우저에서 제대로 보인다** (육안 확인) — 점수 막대가 그려지고,
   `<details>` 섹션이 접히고 펴지고, 네트워크를 끊은 상태에서도 레이아웃이 깨지지 않는다.
   마지막 항목이 CDN 의존이 없다는 증거다.

## M0에서 확인할 것

지금 단정하지 않고 Day 1 첫 슬롯에서 실측할 항목이다. `scout doctor`가 1~2번을 찍어준다.

### 1. Bedrock 모델 ID 형태

`anthropic.claude-sonnet-5` / 크로스리전 프로파일 `us.anthropic.claude-sonnet-5` /
inference profile ARN 중 계정 설정에 따라 다르다. `doctor`가 `ListFoundationModels`로
찍어보고 `config.py` 기본값을 정한다.

### 2. Bedrock 동시 호출 쿼터

`verify`가 judge를 8~10회 부른다. 쿼터가 낮으면 `Semaphore`를 조인다.
`doctor`에서 4병렬 호출로 확인.

### 3. DuckDuckGo 패키지 이름

`duckduckgo-search`가 `ddgs`로 개칭된 이력이 있다. `uv add` 시점에 유효한 이름을 확인해 고정.

### 4. `ty`의 Pydantic 이해도

`schemas.py`가 코드의 중심이라 여기 오탐이 쏟아지면 값이 없다. 그날 바로 끄고 넘어간다.
프리뷰 도구와 씨름하는 데 2일 중 시간을 쓰지 않는다.

### 5. `.with_structured_output`의 Bedrock 동작

tool-use 기반이라 될 것으로 보지만, `include_raw=True`로 파싱 실패 시 원본을 잡아 재시도
경로를 둔다. `Verdict`처럼 필드가 많은 스키마에서 특히 확인.

### 6. `ChatBedrockConverse`의 effort 전달

`additional_model_request_fields` 경유 가능 여부. 프로토타입에선 기본값으로 두고 넘어간다.

### 7. Bedrock 인증 방식

**Access Key 방식으로 확정** — `AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY` · `AWS_DEFAULT_REGION`.
자격이 없으면 그 자리에서 막히므로 **STEP 00의 첫 확인 대상**이다. `doctor`가 찍을 것:

1. `sts get-caller-identity` 성공 여부 (Access Key가 살아 있는가)
2. `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` **존재 여부만** (값은 찍지 않는다)
3. 설치된 `boto3` · `langchain-aws` 버전
4. `ListFoundationModels` 로 사용가능 모델 + 모델 ID 형태
5. Sonnet 1회 호출 + 4병렬 호출

### 8. `jinja2`가 이미 설치돼 있는지

`report.py`가 HTML 템플릿을 쓴다. `langchain-core`가 `jinja2`를 끌어올 가능성이 있어
실제 추가 의존성은 0일 수도 있다. `uv sync` 후 `uv pip show jinja2`로 확인하고,
없으면 `uv add jinja2`.

[08-설정](08-설정.md)의 `env` 필터를 쓴다.

## 비용

Bedrock 요금은 AWS 체계다 — 단가는 AWS 콘솔에서 확인한다.

프로토타입 기본 규모(요소 3개 · 후보 8~10개 · judge 8~10회)에서 1회 실행은 대략
**입력 100~150k / 출력 25~35k 토큰**. `--max-components 8`로 풀 규모로 돌리면 3배 정도.
`report`는 LLM을 쓰지 않으므로 토큰이 0이다.
Day 2에 `usage_metadata`를 콜백으로 집계해 실측한다.
