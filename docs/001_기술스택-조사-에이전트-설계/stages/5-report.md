## 목적

의사결정에 쓸 수 있는 문서를 만든다. 그리고 **사람들이 실제로 열어보고 싶게** 만든다.

마크다운 표로는 후보 비교가 눈에 안 들어온다. `overall 4 · maturity 5 · risk 3`을 숫자로
읽는 것과 막대 길이로 보는 것은 다르다. 후보를 고르는 일은 본질적으로 비교이므로,
**비교가 시각적으로 드러나야 한다.**

그리고 점수 옆에 **왜 그 점수인지**가 있어야 한다. 숫자만 있으면 읽는 사람이
judge의 판단을 검증할 수 없다.

## LLM을 쓰지 않는 이유

2일 예산에서 **가장 큰 절약이 이 결정이다.**

| 이득 | 설명 |
|---|---|
| 프롬프트 튜닝 시간이 0 | 보고서 문체를 다듬는 데 반나절이 사라지는 걸 막는다 |
| 매번 같은 형식 | 실행마다 섹션이 달라지지 않는다 |
| 값이 빠지면 즉시 보인다 | 템플릿에 구멍이 나면 눈에 띈다. LLM은 빈 값을 매끄럽게 메워버린다 |
| 환각 경로가 없다 | 이 단계에서 새 주장이 생길 수 없다 |

`evaluate`가 구조화된 결과를 냈으므로 렌더링할 재료는 이미 다 있다.
요약 문장이 필요한 곳은 `verdicts.solves_reason`을 그대로 인용한다.

### 그대로 인용하되 문단으로 끊는다

judge의 문장을 **고치지 않는다**는 것과 **한 덩어리로 찍는다**는 것은 다르다. 실측에서
`stack_rationale`이 한 문단 630자였고, 저장된 값에 **줄바꿈이 하나도 없어서**
(`scout.db` 전 필드에 `\n` 0개) 화면이 글자 벽이 됐다. CSS `white-space: pre-wrap`은
이미 걸려 있었지만 접을 줄바꿈이 공급되지 않아 무효였다.

그래서 `sentences` 필터가 **문장 경계에서만 끊는다.** 요약도 재작성도 아니고 자르기만
하는 정규식이라 불변식 7과 무관하다 — 새 주장이 생기지 않는다. 버전(`4.17.11`)·
금액(`$200`)·약어에서 끊기지 않게 한국어 종결(`다.`·`요.`)을 우선한다.

한계: judge가 **한 문장으로 300자**를 쓰면 그 문장은 끊기지 않는다. 문장 안을 자르는 건
고치는 것이라 하지 않는다. 그 경우는 `interview`·`evaluate` 프롬프트가 다룰 문제다.

### 같은 문장을 두 번 읽게 하지 않는다

한 값이 여러 섹션에 인용되면 **전문은 한 곳에만** 둔다. 둘째 출현부터는 `<details>`로
접고 `<summary>`에 첫 문장만 보인다. 지우는 게 아니라 접는 것이므로 불변식 12와
충돌하지 않는다.

| 값 | 전문이 있는 곳 | 접히는 곳 |
|---|---|---|
| `winner_reason` | 선택한 기술 (표) | 결정 지점별 비교 |
| `rejected_reason` | 탈락 사유 | 결정 지점별 비교 |
| `solves_reason` | 결정 지점별 비교 (접힌 본문) | — |

실측에서 200자 넘는 블록 6종이 한 문서에 정확히 2번씩 나와 체감 분량이 2배였다.

## HTML 제약 — self-contained 단일 파일

| 규칙 | 이유 |
|---|---|
| **외부 CDN 없음** | 사내 환경에서 CDN 접근이 막힐 수 있다. 파일 하나로 공유돼야 "쉽게 볼 수 있다"가 성립한다 |
| **JS 0줄** | 차트 라이브러리를 안 쓴다. 아래 방식으로 JS 없이 다 된다 |
| **인라인 CSS** | `<style>` 블록 하나. 별도 파일 없음 |
| 이미지 없음 | 아이콘은 유니코드 문자로 |

### JS 없이 하는 것들

| 하고 싶은 것 | 방법 |
|---|---|
| 점수 막대 차트 | `<div style="width: {{ score * 20 }}%">` — 5점 척도면 CSS 폭 하나 |
| 근접 배지 | `{% if margin == "close" %}` + CSS 클래스 |
| 접히는 섹션 | `<details>` / `<summary>` — 브라우저 기본 기능 |
| 근거 툴팁 | `title` 속성, 또는 수집한 사실로 앵커 링크 |
| 배지 (`계산`/`판정`/`근거 없음`, 신뢰도, 근거 위반) | CSS 클래스 + 배경색 |
| 다크모드 | `@media (prefers-color-scheme: dark)` |

정렬·필터는 넣지 않는다. 요소 3개 · 후보 8~10개 규모에서는 정렬할 것이 없다.

### 템플릿 엔진

`jinja2`를 쓴다. HTML을 f-string으로 짜면 Day 2에 시간을 잡아먹고 유지보수가 나쁘다.
`langchain-core`가 이미 끌어올 가능성이 있으므로 실제 추가 의존성은 0일 수도 있다 —
M0에서 확인한다 ([07-검증](../07-검증.md)).

템플릿은 `scout/templates/report.html.j2` 한 파일.

## 입력

`scout.db` 전체. SQL로 필요한 것만 꺼낸다.

| 섹션 | 쿼리 대상 |
|---|---|
| **권장 설계** (확정본) | `final_designs` (slug당 1행) |
| **기본 설계** (조사 전) | `designs` (slug당 1행) |
| 결정 요약 | `picks` (rank=1, `winner_reason`) + `scores` + `runs.interview_json` |
| **이미 정해진 것** | `components` (`needs_comparison = false`) |
| 지금 만들지 않아도 되는 것 | `components` (necessity IN ('defer','unnecessary')) |
| 이번에 다루지 않은 것 | `components` (essential/valuable + 비교 대상이지만 priority 밀려 통과 못 함) |
| 결정 지점별 비교 | `picks` + `verdicts` + `scores` |
| 탈락 사유 | `picks` (rank IS NULL) + `verdicts.solves_reason` |
| 수집한 사실 | `facts` + `citations` |

`designs`와 `final_designs`는 **`shape`·`data_flow`를 같은 이름으로** 준다 —
같은 필드의 v1·v2다. 조인 없이 나란히 렌더링하면 그게 곧 대조표가 된다.

`report`는 LLM을 쓰지 않으므로(불변식 7) 여기서 문장을 다듬을 수 없고, **고르기만** 한다.
`title`이 비었거나 60자를 넘으면 `runs.description`(사용자 원문)으로 물러난다.

### 1. 최상단 — 권장 설계 (`final_designs`)

**사용자가 이 보고서를 열어서 가장 먼저 읽어야 하는 것.** `evaluate`가 쓴
`FinalDesign` 한 행을 그대로 렌더링한다. 순서가 중요하다.

```
summary                 확정된 설계 한 단락
shape · data_flow       ★ 확정된 구조와 흐름 — 이게 "수정 설계"의 본문이다
조사로 바뀐 것    ★ changes_from_design
build_order             구축 순서
integration_notes       연동 지점
combination_risks       조합 위험
unresolved              미해결
```

"요소별로 이걸 골랐다"와 "**이 구조로 이렇게 만들면 된다**"는 다른 답이다.
선택한 기술 표(3번)는 선택의 목록이고, 이 섹션은 **조사를 거쳐 수정된 설계도**다.

#### "조사로 바뀐 것" (`changes_from_design`)

이 도구가 값어치를 증명하는 자리다 — **조사가 설계를 바꿨다는 증거**다.

```
조사로 바뀐 것
  · 요약 워커를 백엔드 프로세스에서 분리했다 — 같은 프로세스면 LLM 호출 지연이
    WebSocket 이벤트 루프를 막는다 (socket.io 판정의 caveats)
```

**비어 있으면 섹션을 지우지 않는다** — "조사 결과가 기본틀을 바꾸지 않았다"를 쓴다.
기본틀이 조사를 견뎠다는 것도 정보다 (불변식 12).

`final_designs` 행 자체가 없으면(설계 확정 실패) 역시 지우지 않는다 — "설계 확정
실패 + `gaps`의 이유"를 같은 자리에 찍는다.

### 2. 설계 개요 — v1 대조 (`<details>`, `designs`)

`design` 단계의 `Architecture` — **조사 전 기본틀**이다.
`shape` · `data_flow`를 **1번의 확정본과 나란히** 두어 무엇이 바뀌었는지 눈으로 볼 수
있게 한다. 확정본이 위에 있으므로 이쪽은 접어둔다.

```
▼ 설계 개요 (조사 전 기본틀)
   구조         기본틀: …            →  확정: …
   데이터 흐름   기본틀: …            →  확정: …
   미해결 질문   open_questions
```

`report`는 LLM을 쓰지 않는다(불변식 7). **대조는 같은 이름의 필드를 나란히 놓는 것**이고,
무엇이 왜 바뀌었는지를 문장으로 쓰는 것은 `evaluate`의 `changes_from_design`이 한다.
두 테이블이 `shape`·`data_flow`를 같은 이름으로 갖는 이유가 이것이다
([03-저장](../03-저장.md)).

`open_questions`는 특히 지우지 않는다 — 설계가 답하지 못한 것을 답한 척하지 않는 게
이 섹션의 일이다.

### 3. 결정 요약 (스크롤 없이 보이는 범위)

- **선택한 기술 표** — 요소 / 고른 것 / **`overall` 막대** / **`winner_reason` 한 줄**.
  `margin`이 `close`면 `[근접]` 배지를 붙인다 — "2위도 합리적 선택"이라는 뜻이다.
  점수는 가중 합산이 아니라 judge가 매긴 종합 판단이다
- **가장 큰 위험 3개** — `verdicts.cons`와 `caveats`에서 뽑는다
- **명시된 가정** — `runs.interview_json`의 `assumptions`.
  사용자가 답하지 않아 기본값을 쓴 항목이 여기 드러난다
- **구체화된 명세** — `refined_brief` 전문. 이 판단이 무엇을 전제했는지 보여준다.
  범위 제외("이번엔 안 한다") 같은 것도 별도 필드가 아니라 이 문단 안 문장으로만 있고,
  `report`는 LLM이 없어 프로즈에서 항목을 뽑아 세지 못하므로 **개수를 세는 대신 전문을
  보여준다.** 다만 문장 단위로 끊어 싣는다 (위 "그대로 인용하되 문단으로 끊는다").

  ★ **헤더가 아니라 여기다.** 구현이 한때 이걸 `<h1>` 바로 아래 부제로 올려놨는데,
  실측 254자 문단이 제목 밑에 벽으로 섰다. 헤더의 둘째 행은 `constraints` 칩이다

### 4. 이미 정해진 것

`needs_comparison = false`인 결정 지점 + `no_comparison_reason`.

**권장 설계가 깔고 있는 전제를 드러내는 자리다.** 설계는 "3인 TypeScript 팀"을 전제로
세웠는데 보고서에 그 전제가 안 보이면, 사용자는 왜 다른 언어를 검토하지 않았는지
알 수 없다. 조사를 안 한 것과 **조사할 필요가 없다고 판단한 것**은 다르고,
그 차이를 말하는 게 이 섹션이다.

`needs_comparison`이 전부 `true`여서 이 섹션이 비면 `design`의 프롬프트 반례가 안 먹힌
신호다 — [1-design.md](1-design.md) 참조.

### 5. 지금 만들지 않아도 되는 것

`design`의 `defer` / `unnecessary` 결정 지점 + `necessity_reason`.

**사용자가 가장 놀라는 섹션이라 위쪽에 둔다.** 다른 도구는 "이것도 필요하고 저것도 필요하다"만
말한다. 이 섹션이 비어 있으면 `design`의 필요성 판단이 작동하지 않은 것이다
([07-검증](../07-검증.md) 성공 기준 7번).
`test_necessity_wiring.py`가 이 섹션에 요소가 렌더링되는지 자동으로 검사한다.

### 6. 이번에 다루지 않은 것

`--max-components`로 통과하지 못한 요소를 명시한다.
**조용히 사라지면 안 된다** — "더 보려면 `--max-components 8`로 다시 돌리세요"를 함께 적는다.

### 7. 다음 명령어 (`<details>`)

초기화 명령, 폴더 구조, 첫 스프린트 티켓 3개.
실용성이 여기서 갈린다 — 보고서를 읽고 나서 무엇을 타이핑해야 하는지 알아야 한다.

### 8. 결정 지점별 비교

후보마다 막대 3개 — **`overall`(judge) · `maturity`(계산) · `risk`(계산)**.
계산할 숫자가 없으면 막대 대신 `근거 없음` 배지
(`method` 후보는 이게 정상이다 — 낮은 게 아니라 없는 것).

**`score_reason`을 막대 바로 아래 둔다.** 숫자와 이유가 떨어져 있으면 읽는 사람이
숫자만 보고 넘어간다. 이게 이 섹션의 요점이다.

1위에는 **`winner_reason`**(제약 인용 + 2위와의 점수 차이)을,
2위에는 **`runner_up_note`**를 붙인다. 탈락 후보는 취소선 + 탈락 이유 한 줄.

### 9. 탈락 사유 (`<details>`)

`solves_reason`을 그대로 인용한다. **신뢰도가 여기서 나온다** —
왜 안 골랐는지 설명할 수 있는 도구와 못 하는 도구는 다르다.

### 10. 수집한 사실 (`<details>`)

`fact_id` → label / value / url / 조회일 표.

함께 표시하는 배지:

| 배지 | 뜻 |
|---|---|
| `confidence: low` | 근거가 얕았다 |
| `grounding 위반` | judge가 없는 사실을 인용하려 했다 |
| `computed` | dossier 숫자로 계산됐다 |
| `judged` | judge가 판단했다 (`overall`) |
| `근거 없음` | 계산할 숫자가 없다 (`source=unavailable`) |
| `gaps` | 못 구한 사실 |

**이 섹션이 "판단"과 "사실"을 분리해 보여주는 자리다.**
읽는 사람이 어디까지 믿어야 할지 스스로 정할 수 있어야 한다.

## 터미널 출력

HTML만 만들면 터미널에서 아무것도 안 보인다. `report`도 다른 단계와 같은 배너
패턴을 쓴다 — "[리포트] 단계를 시작합니다."로 열고, 요약을 찍은 뒤
"...종료합니다."로 닫는다(`scout/cli.py`, 02-파이프라인.md "실행 흐름").
파이프라인 마지막 단계이므로 그 뒤에는 `report.html` 경로가 찍힌다.

```
[리포트] 단계를 시작합니다.
  권장 설계: 단일 Node 백엔드에 socket.io로 실시간 전달을 얹고 메시지는
            PostgreSQL 한 곳에 저장한다. 요약은 같은 프로세스의 주기 워커가 맡는다.

  실시간 메시지 전달   socket.io            4  (근접)
  메시지 저장         PostgreSQL           5
  LLM 요약 호출       Bedrock 직접 호출     4

  걸러낸 결정 지점 2개 · 이미 정해진 것 2개 · 탈락 후보 3개 · 근거 위반 0건
[리포트] 단계를 종료합니다.

[OK] slug=2026-09-02-team-chat
리포트: runs/2026-09-02-team-chat/report.html
```

마크다운은 만들지 않는다. 두 형식을 유지하면 둘 다 반쯤 된다.

## 출력

`runs/<slug>/report.html` 한 파일. 브라우저로 열면 끝이고, 그대로 첨부해 공유할 수 있다.

## 실패 처리

| 상황 | 동작 |
|---|---|
| 특정 섹션의 데이터가 비어 있음 | 섹션을 지우지 않고 "해당 없음" + 이유를 쓴다. 조용히 사라지면 안 된다 |
| 요소의 통과 후보가 0개 | 결정 요약에 경고로 노출 |
| `evaluate`까지 못 갔음 | 있는 단계까지만 렌더링하고 "미완료" 배너 표시 |
| `jinja2` 미설치 | M0에서 확인. 없으면 `uv add jinja2` |

**빈 섹션을 감추지 않는 게 원칙이다.** 없는 걸 없다고 말하는 게 보고서의 일이다.

## 절단 시

절단 대상이 아니다. LLM을 쓰지 않으므로 API 비용이 0이다.

시간이 부족하면 **HTML의 꾸밈만 줄인다** — 막대 차트와 `<details>`는 각각 CSS 한 줄과
HTML 태그 하나라 사실상 공짜다. 다크모드와 배지 색상이 먼저 잘릴 후보다.

잘라낸 것 중 이 단계와 관련된 것:

- **ADR 생성** — 되돌릴 수 없는 결정마다 별도 파일을 만드는 것.
  지금은 "결정 요약"과 "탈락 사유" 두 섹션이 그 역할을 얕게 대신한다
- **정렬·필터 UI** — 요소 3개 규모에서는 필요 없다. JS를 넣게 되는 지점이라 특히 미룬다
