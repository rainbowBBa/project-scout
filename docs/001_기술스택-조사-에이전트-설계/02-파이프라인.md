## 6단계

| # | 단계 | 하는 일 | 쓰는 테이블 | LLM |
|---|---|---|---|---|
| 0 | [**interview**](stages/0-interview.md) | 되묻기 — 막연한 요청을 **구체화** | `runs` | O |
| 1 | [**design**](stages/1-design.md) | **구현 설계** + 비교가 필요한 결정 지점 도출 + **필요성** | `designs` `components` | O + MCP |
| 2 | [**search**](stages/2-search.md) | 결정 지점별 방법·소프트웨어·라이브러리 조사 + **dossier** 수집 | `candidates` `facts` `gaps` | O + MCP |
| 3 | [**verify**](stages/3-verify.md) | **LLM-as-judge** — 장단점 + 해결가능성, 인용 강제 | `verdicts` `citations` | O (judge) |
| 4 | [**evaluate**](stages/4-evaluate.md) | 계산 점수 + judge 종합 점수 → 순위 · 선정 + **설계 확정** | `scores` `picks` `final_designs` | O |
| 5 | [**report**](stages/5-report.md) | **단일 HTML 렌더링** | → `report.html` | X |

### 이름 규칙

단계명은 **동사 한 단어**로 통일한다. 모듈 파일명 · LangGraph 노드명 · CLI 인자가 모두 같은
단어를 쓴다. 외울 게 6개뿐이고, 어디를 고쳐야 하는지 이름만 보고 짚힌다.

```
scout/stages/verify.py   →   scout show <slug> verify
```

Pydantic 스키마는 명사로 둔다 — **단계는 동사, 데이터는 명사**:
`Interview` · `Design`(+`Architecture`·`Component`) · `Candidate`(+`Fact`) · `Verdict` ·
`ElementPick` · `FinalDesign`

`design`은 동사와 명사가 같은 단어다. 단계는 `design`, 스키마는 `Design`으로 두고
혼동을 감수한다 — 대안(`plan`·`architect`)은 이 단계가 하는 일을 덜 정확하게 말한다.

## 실행 흐름

CLI는 서브커맨드 없이 `uv run scout`만 실행해도 파이프라인을 돈다 — 설명은
그 자리에서 대화형으로 입력받는다. 각 단계는 "[단계] 단계를 시작합니다."로
열리고, 그 단계의 결과를 사람이 읽기 좋게 요약해 보여준 **다음에**
"...종료합니다." 배너로 닫힌다 — 요약이 종료 배너보다 먼저 나온다
(`scout/cli.py`, 원본 JSON은 `scout show <slug> <단계>`로 본다).

```
$ uv run scout
프로젝트 설명 입력: AI 요약 기능이 있는 팀 채팅 앱을 만들고 싶어

[인터뷰] 단계를 시작합니다.
  ? 몇 명 정도가 사용할 앱인가요?: 사내 200명
  ? 개발팀 구성은 어떻게 되나요?: 3명, TypeScript
  ? 예산은 어느 정도로 생각하고 계세요?: 월 $200 정도
  ? 데드라인은 언제까지인가요?: 3개월 안에는 내고 싶어요
(LLM이 충분하다고 판단 — 대화 종료)
  구체화된 설명: 사내 200명이 쓰는 팀 채팅 앱. 실시간 전달과 AI 요약이 핵심
  기능. 3인 TypeScript 팀이 3개월 내 출시, 월 예산 $200.
  가정: (없음 — 전부 응답함)
[인터뷰] 단계를 종료합니다.

[설계] 단계를 시작합니다.
  · 설계 탐색 시작 — 툴 최대 10 superstep
  · npm_search "socket.io node.js websocket server"
  · npm_search "postgres client node typescript"
  · 설계 추출
  설계: 3인 팀이 3개월에 200명을 감당해야 하므로 직접 운영할 컴포넌트를 최소로 묶는다.
        단일 Node 백엔드가 실시간 연결과 REST를 함께 처리하고, 메시지는 관계형 DB
        한 곳에 저장한다. AI 요약은 주기 작업으로 분리해 채팅 지연에 영향을 주지 않는다.
  무엇부터: 메시지 저장 스키마 → 실시간 전달 → 인증 → 요약 워커 → 배포·관측

  통과 3개 (자세히: scout show 2026-09-02-ai-summary-team-chat design)
    [essential] 실시간 메시지 전달 (feature) — priority 1
      정할 것: 200 동시 연결·재연결·룸 브로드캐스트를 3인 팀이 운영 부담 없이
              쓸 수 있는 전달 계층은 무엇인가
      힌트: socket.io, ws websocket library node, server-sent events chat
    [essential] 메시지 저장 (data) — priority 2
      정할 것: 메시지와 요약 결과를 한 트랜잭션에 묶을 수 있는 저장소는 무엇인가
      힌트: postgresql node client, sqlite wal concurrent writes
    [essential] LLM 요약 호출 (integration) — priority 3
      정할 것: 주기 워커에서 논블로킹으로 요약을 돌릴 호출 계층은 무엇인가
      힌트: bedrock runtime sdk node, llm summarization batch queue
[설계] 단계를 종료합니다.
```

질문 문구·순서는 매번 LLM이 그 자리에서 판단해 만드므로 실제로는 매 실행마다
다르다 — 위는 한 가지 예시일 뿐이다. 단계 요약에는 **통과한 결정 지점만** 나온다.
`defer`/`unnecessary`로 걸러진 것("메시지 전문검색 — 200명이면 LIKE로 충분")과
설계에서 이미 닫힌 것("서버 런타임·언어 — 3인 TypeScript 팀")은
`scout show <slug> design`으로 전부 본다.

`search`는 결정 지점마다 ReAct 에이전트를 돌리고, 웹검색은
**나가기 전에 사람 승인을 받는다** — 화면에 아래가 끼어든다.

```
[검색] 단계를 시작합니다.

  · 결정 지점 3개 조사 시작
  · 실시간 캔버스 동기화 — 조사 시작
  ? 인터넷 검색 "CRDT conflict-free replicated data type real-time canvas" — 허용할까요? [y/N]: n
  ? 거부 사유: 고유명사·제품명을 질의에 넣지 마세요
  ? 인터넷 검색 "operational transformation collaborative editing architecture" — 허용할까요? [y/N]: y
  · 실시간 캔버스 동기화 — 후보 추출
  후보 2개 (자세히: scout show 2026-09-02-ai-summary-team-chat search)
    [library] yjs — 실시간 캔버스 동기화
      사실 7개: npm.latest_version, npm.last_release, npm.license, gh.last_commit, …
[검색] 단계를 종료합니다.
```

거부하면 사유가 에이전트에 돌아가 **질의가 바뀐 채로 다시 승인을 요청한다.**
`--auto-approve-search`를 주면 `· 인터넷 검색 "…" — 자동 승인`으로 찍고 통과한다
(비대화형 재현용). 무엇이 나갔는지는 그대로 보여준다.

출력 줄의 종류와 규칙은 [09-출력양식](09-출력양식.md)이 정본이다.

`design`은 같은 게이트를 쓰지만 예산이 다르다 — **실행 전체에서 3회**다
(`search`는 결정 지점당 5회). 설계는 요소별로 펼치지 않고 한 번 돌기 때문이다.

이후 단계도 같은 배너 패턴을 그대로 잇는다.

```
verify      LLM-as-judge. 후보 하나하나 독립 판정
            → verdicts / citations
              socket.io  solves_it=true   confidence=high
                pros: 재연결·룸·폴백 내장   cons: 프로토콜 독자규격
                citations: [npm.last_release, gh.last_commit, osv.vulns]
              sockjs     solves_it=false  confidence=high
                solves_reason: "마지막 릴리스 2021-01-14, 커밋 3년 전 — 유지보수 중단"
                citations: [npm.last_release, gh.last_commit]
            → grounding.py 가 citations ⊆ dossier 를 SQL로 검증

evaluate    maturity·risk를 코드가 계산하고, judge가 종합 점수(overall)를 매긴다
            → scores / picks
              scores   socket.io  overall 4 judged   maturity 5 · risk 5 computed
                         ↳ "릴리스 11일 전, 재연결·룸 내장. 독자 프로토콜이 5를 막음"
                       ws         overall 3 judged   maturity 4 · risk 5 computed
              picks    winner=socket.io  margin=close
                         winner_reason "overall 4 vs ws 3 — 3인 팀 3개월에 부담 작음"

            요소별 순위가 끝나면 LLM을 한 번 더 불러
            design의 기본틀을 조사 결과로 수정해 확정한다
            → final_designs
              summary  "단일 Node 백엔드에 socket.io로 실시간 전달을 얹고,
                         메시지는 PostgreSQL 한 곳에 저장한다"
              shape · data_flow  ← designs의 같은 필드를 수정한 v2
              changes_from_design
                "요약 워커를 백엔드 프로세스에서 분리했다 — 같은 프로세스면
                 LLM 지연이 이벤트 루프를 막는다 (socket.io 판정의 caveats)"
              integration_notes "룸 이름과 채널 ID를 같은 값으로 쓴다 …"
              combination_risks "단일 프로세스 전제가 깨지면 어댑터가 필요해지고 …"

report      LLM 아님. scout.db 를 jinja2 템플릿으로 렌더링 (CDN·JS 없음)
            최상단이 final_designs — "이 구조로 이렇게 만들면 되겠다"
            designs를 <details>로 나란히 둬 v1↔v2 대조를 보여준다
            → report.html
```

파이프라인 마지막에 `report.html` 경로를 보여준다.

## 부가 명령

```
$ uv run scout                          기본 진입점 — 서브커맨드 없이 실행하면
                                         설명을 대화형으로 물어보고 파이프라인 전체를 돈다
$ uv run scout doctor                  AWS 자격·리전·모델·동시호출 쿼터 확인 (Day 1 첫 작업)
$ uv run scout show <slug> verify      특정 단계 결과 열어보기 (단계명 그대로 인자)
$ uv run scout run "..." --stop-after search    중간까지만 실행
$ uv run scout run "..." --from verify          중간부터 재실행
$ uv run scout run "..." --max-components 8     규모 확대 (기본 3)
$ uv run scout run "..." --max-candidates 5     요소당 후보 수 (기본 3)
```

`run` 서브커맨드(설명을 인자로 직접 넘기고 개발용 플래그를 쓰는 형태)는 개발 중
반복 실행에 쓴다. 호출 수를 줄이는 **개발 프로파일**(규모 축소 + LLM 캐시)은
CLAUDE.md "명령" 절과 [08-설정](08-설정.md)에 있다. 사용자에게 보여주는 기본 경험은 서브커맨드 없는 `uv run scout`다.

`--from`은 `verify` 프롬프트를 고칠 때마다 앞 단계를 다시 돌리지 않게 해주려던 장치다 —
그래서 저장이 인메모리가 아니어야 한다([03-저장](03-저장.md)).

**아직(2026-09-03) `--from`은 값만 검증하고 실제로 앞 단계를 건너뛰지 않는다** —
그래프가 항상 START(`interview`)부터 돈다. 중간부터 다시 도는 것은 전적으로
`SqliteSaver` 체크포인터가 한다(끝난 노드를 건너뛴다). 그 결과로 **프롬프트만 고쳐서
특정 단계를 다시 돌리는 건 지금 안 된다** — 체크포인트가 그 노드를 이미 끝난 것으로
보기 때문이다. 새 slug로 돌리거나 `runs/<slug>/checkpoints.sqlite`를 지운다.

`--stop-after`는 실제로 그 단계 뒤에서 멈춘다(스트림 루프가 해당 노드 처리 후 끊는다).
실제 건너뛰기는 필요해지는 STEP에서 만든다.

## 오케스트레이션

LangGraph `StateGraph`. 단계가 노드, 상태는 `ScoutState`(TypedDict).

- **fan-out**: `verify`는 `Send` API로 후보별로 펼친다. **`search`는 노드 하나가
  내부에서 `asyncio.gather`로 요소를 펼친다** — `Send`를 쓰면 한 superstep에 여러
  노드 키가 올라와 `cli.py`의 스트림 루프(첫 키만 읽는다)와 단계 배너가 깨진다
  ([stages/2-search](stages/2-search.md) "동시성")
- **동시성**: 단계 내 `Semaphore`로 제한 (LLM 4, MCP 8).
  MCP 서버 자체 레이트리미터와 이중 방어
- **조건 엣지**: 요소 0개 / 후보 0개면 조기 종료하고 이유를 보고서에 남긴다
- **재개**: `SqliteSaver` 체크포인터, `thread_id = run slug`. 전용 `scout resume`
  커맨드는 아직 없다 — 지금은 `scout run "..." --from <단계>`로 중간부터 다시
  돈다(실제로 해당 단계 앞을 건너뛰지는 않는다, "부가 명령" 참고)

## 이 파이프라인의 세 가지 원칙

### judge는 사실을 만들 수 없다

`verify`의 LLM은 dossier에 있는 사실만 `fact_id`로 인용할 수 있고, 그 집합 밖을 인용하면
코드가 잡아낸다.

### 필요성 판단이 앞에 있다

안 만들어도 되는 요소는 `search`에 아예 들어가지 않는다. 후보 수·토큰·시간이 함께 줄고,
보고서에 "지금 만들지 않아도 되는 것" 섹션이 생긴다.

### 단계마다 결과가 디스크에 남는다

중간에 끊겨도 재개되고, `candidates`/`facts`를 손으로 고쳐서 `verify`부터 다시 돌릴 수 있고,
결과가 이상할 때 어느 단계가 틀렸는지 바로 짚힌다.
